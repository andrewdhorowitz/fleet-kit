# Publish registry — schema and generated index (no copies)

**There are no manifest copies here anymore.** One project = one repo
(Andrew's rule, Oct 29, 2026): each project's `publish.json` lives
only at that repo's root, and every consumer pulls it from there.
Project repos have zero dependency on each other; this directory is
shared infrastructure — the one layer projects may all lean on.

What lives here:

- **[`publish.schema.json`](publish.schema.json)** — the fleet
  schema every `publish.json` validates against. It lives in
  fleet-kit because the schema is shared infrastructure, not any one
  project's data.
- **`private-hosts.json`** — GENERATED by
  [`scripts/pull_publish.py`](../scripts/pull_publish.py), never
  edited by hand. It carries only the fleet's declared-private host
  strings (with the project and source repo for each, and the source
  manifest blob SHAs so staleness is checkable). It exists for one
  consumer: the portfolio's publish gate, which runs in the public
  portfolio repo's CI, where private repos cannot be read — the gate
  needs the denylist, and host strings are not secret. Regenerate it
  whenever a manifest's `private_hosts` change (the pull tool
  validates every manifest against the schema in the same run).

Who reads manifests, and how:

- **The private section** (`andrewdhorowitz/private-section`)
  generates its index by pulling each project's `publish.json` from
  that project's repo at generation time. Its output records the
  manifest blob SHA each entry was built from.
- **The portfolio publish gate** (`andrewdhorowitz.github.io`,
  `.github/workflows/publish-gate.yml`) checks this repo out at CI
  time and reads only the generated index above; it fails the
  portfolio build if any page links to a declared-private host.
- **A project's card links only that project's own surfaces.** A
  card's Repo link is structural — the repo its data was pulled
  from — and Repo links are owner-view only: the family dataset
  never carries one (see the spec, fleet records).

The `section` object in a manifest opts the project into the private
index section (gated; never linked publicly). `family_visible` is an
explicit yes — it is for surfaces that carry the family's own data
(the cards), not for general tooling. The optional `also` list names
companion surfaces of the SAME project (e.g. the Fleet Kit's
error-reporter companion); a companion may not link another
project's repo — that project gets its own manifest instead. An
optional `status` in `section` (or on an `also` item) overrides the
badge the index shows for that entry, for when the entry itself
differs from the project's public posture: Family Cards is
`demo-only` as a posture (only its demo may be linked publicly), but
the index entry is the live tool itself, so its section status is
`live`. Without the override, the badge falls back to the manifest
`status`. An optional `link_audiences` in `section` narrows a link
kind to one audience (`owner` / `family`); it can only narrow —
`repo` is owner-only by construction.

First pass (Oct 29, 2026): andrewdhorowitz.github.io,
routines-and-streaks, aimf-protocol, family-cards-demo, family-cards,
fleet-kit. Repo Template gained its own manifest the same evening,
when its card was found living inside fleet-kit's data as a
cross-repo companion link; it is the seventh.

**Intentional dual listing (Andrew, Oct 29, 2026):** the publishing
system lists itself twice on purpose — the restructure work appears
as a Projects entry (in the portfolio manifest's `also` list) and the
manifest/gate/index machinery appears as a Shared Infrastructure entry
(in fleet-kit's `also` list). Tooling must not flag the pair as a
duplicate-name defect.
