# Publish registry — schema and generated index (no copies)

**There are no manifest copies here anymore.** One project = one repo
(Andrew's rule, Oct 29, 2026): each project's `publish.json` lives
only at that repo's root, and every consumer pulls it from there.
Project repos have zero dependency on each other; this directory is
shared infrastructure — the one layer projects may all lean on.

What lives here:

- **[`publish.schema.json`](publish.schema.json)** — the fleet
  schema every `publish.json` validates against. It lives in
  fleet-kit because the schema is shared infrastructure, not any one
  project's data.
- **`private-hosts.json`** — GENERATED by
  [`scripts/pull_publish.py`](../scripts/pull_publish.py), never
  edited by hand. It carries the fleet's declared-private host
  strings (with the project and source repo for each, and the
  source manifest blob SHAs so staleness is checkable) and, since
  the property model landed (Oct 30, 2026), each repo's derived
  property view (see "Derived property view" below). It exists
  for the portfolio's publish gate, which runs in the public
  portfolio repo's CI, where private repos cannot be read — the
  gate needs the denylist, and host strings are not secret.
  Regenerate it whenever a manifest's `private_hosts` change (the
  pull tool validates every manifest against the schema in the
  same run).
- **`packets/`** — sanitize-pass work packets
  ([`scripts/sanitize_packet.py`](../scripts/sanitize_packet.py)), one
  JSON per repo being remediated; see the "Sanitization pass"
  section below and `packets/README.md`. Identifier hits are
  recorded as hashes + file/line only — a packet never quotes the
  identifier it exists to remove.
- **`sanitize-overlay.json`** — GENERATED by
  [`scripts/pull_sanitize.py`](../scripts/pull_sanitize.py), never
  edited by hand. Per-repo sanitization-gate results for the
  fleet's public/demo surfaces (posture `public`), with quoted
  matches for any failure and the source manifest/head SHAs so
  staleness is checkable. It exists for one consumer: the private
  section's generator, which applies the visible fallback below.

Who reads manifests, and how:

- **The private section** (`andrewdhorowitz/private-section`)
  generates its index by pulling each project's `publish.json` from
  that project's repo at generation time. Its output records the
  manifest blob SHA each entry was built from.
- **The portfolio publish gate** (`andrewdhorowitz.github.io`,
  `.github/workflows/publish-gate.yml`) checks this repo out at CI
  time and reads only the generated index above; it fails the
  portfolio build if any page links to a declared-private host.
- **A project's card links only that project's own surfaces.** A
  card's Repo link is structural — the repo its data was pulled
  from — and Repo links are owner-view only: the family dataset
  never carries one (see the spec, fleet records).

The `section` object in a manifest opts the project into the private
index section (gated; never linked publicly). `family_visible` is an
explicit yes — it is for surfaces that carry the family's own data
(the cards), not for general tooling. The optional `also` list names
companion surfaces of the SAME project (e.g. the Fleet Kit's
error-reporter companion); a companion may not link another
project's repo — that project gets its own manifest instead. An
optional `status` in `section` (or on an `also` item) overrides the
badge the index shows for that entry, for when the entry itself
differs from the project's public posture: Family Cards is
`demo-only` as a posture (only its demo may be linked publicly), but
the index entry is the live tool itself, so its section status is
`live`. Without the override, the badge falls back to the manifest
`status`. An optional `link_audiences` in `section` narrows a link
kind to one audience (`owner` / `family`); it can only narrow —
`repo` is owner-only by construction.

First pass (Oct 29, 2026): andrewdhorowitz.github.io,
routines-and-streaks, aimf-protocol, family-cards-demo, family-cards,
fleet-kit. Repo Template gained its own manifest the same evening,
when its card was found living inside fleet-kit's data as a
cross-repo companion link; it is the seventh.

**Intentional dual listing (Andrew, Oct 29, 2026):** the publishing
system lists itself twice on purpose — the restructure work appears
as a Projects entry (in the portfolio manifest's `also` list) and the
manifest/gate/index machinery appears as a Shared Infrastructure entry
(in fleet-kit's `also` list). Tooling must not flag the pair as a
duplicate-name defect.

## Visibility follows mode

Andrew's rule (Oct 29, 2026): a repo's actual GitHub visibility
matches its declared mode. A sanitized repo in **public mode is a
public repo**; a repo in a **private-tier mode (family/owner) is a
private repo**. The mode is declared in the project's own
`publish.json`: status `public` → public repo; status `private` →
private repo; status `demo-only` → private repo (the repo holds the
private live surface — any public demo is a separate project in its
OWN repo); a family-tier section entry (family group or
`family_visible`) also means a private repo. Two fleet repos carry
no manifest, so their modes are declared by role in the spec:
`private-section` is private (the consumer/display), `fleet-ci` is
public (public callers can only call public reusable workflows).

When a mode switches, the repo's visibility switches **in the same
pass** — the mode edit and the flip are one change, never two. A
sanitization-gate demotion (public/demo content falls back to
owner-only with a "Sanitizer needed" tag) is a mode switch and
carries the same consequence, subject to the flip guards: **no
automation flips visibility on its own.** Flipping toward public is
an exposure (the whole repo becomes world-readable) and needs
Andrew's explicit word per repo; flipping a GitHub-Pages-hosted
repo toward private can take its site offline (free-plan Pages
needs a public repo).

The check rides the pull tool: every `scripts/pull_publish.py` run
compares each fleet repo's declared mode against its live
visibility and prints one `VISIBILITY MISMATCH:` line per mismatch
(report-only). The Tuesday site-health watch surfaces those lines
in its LEG E report, so a mismatch never sits silent. First audit
(Oct 29, 2026): all nine repos match.

## Derived property view

The publish property model (Andrew's distilled design, approved
Oct 30, 2026) stores nothing in the marker: `publish.json` stays
v2-shaped, and the five properties are a **derived view**, computed
by the fleet's ONE derivation function —
[`scripts/publish_view.py`](../scripts/publish_view.py), in this
shared layer — from the existing fields:

| Property | Derived from |
|---|---|
| **Publish** | marker presence (no marker → `Publish=False`; `Publish=False` is encoded as `status: "private"`) |
| **Tier** | `status` — `public` → Public; `private` → Private; `demo-only` → Private |
| **Shelf** | `section.group`, verbatim (`projects` \| `family` \| `shared-infrastructure`) — the one category axis |
| **Family** | `section.family_visible` |
| **Sanitized** | the sanitize overlay above — never the marker; a stale overlay entry is ignored with a warning, and a repo the gate does not scan has no result (`null`) |

Two rules are non-bypassable, with no exception mechanism anywhere:

1. **Sanitized=False can never be public-facing.** A project is
   public-facing only at Tier=Public with Sanitized=True; an
   unknown result fails that test too.
2. **Family=True forces Tier=Private.** Enforced in the schema
   (the rule clause in `publish.schema.json`:
   `section.family_visible: true` requires status `private` or
   `demo-only`) and in the derivation itself, which refuses the
   combination rather than coercing it. The pull tool fails closed
   with the rule named.

Keys the schema does not declare — a `properties` block, a stray
`force_publish`, a hand-set `sanitized` — are **inert**: the
derivation never reads them, they never fail validation, and the
pull tool reports them as `DRIFT:` lines so they get removed as
ordinary manifest maintenance. A hand-set `sanitized` key in
particular can never manufacture Sanitized=True — Sanitized comes
from the overlay or nowhere.

The pull tool prints each repo's view on every run and records the
views in the generated index (`private-hosts.json`, `views` key)
when it regenerates it — a generated cache of the function's
output, never a second source of truth. The check suite is
[`scripts/test_publish_view.py`](../scripts/test_publish_view.py)
(the seven real manifests plus the hard-rule and drift cases).

## Sanitization gate — public means public AND generic

Andrew's rule (Oct 29, 2026): the main page is public and generic,
and anything labeled a Demo must meet the same bar. Content meant
for a public or demo surface that is not sanitized — a family
identifier, or an off-limit topic from the standing sensitive
categories — falls back to owner-only: it does not ship publicly,
and it does not drop to the family tier instead. (Live family apps
with live data are a separate track, out of this gate's scope.)

The checker is [`scripts/check_sanitize.py`](../scripts/check_sanitize.py)
(stdlib only), driven by ONE term file,
[`scripts/sanitize_terms.json`](../scripts/sanitize_terms.json):

- **Identifiers** (family names, family emails, home/school/street
  identifiers) are definite hits, stored in the term file as SHA-256
  hashes of their normalized forms — this repo is public, and a
  plaintext forbidden-names list would itself publish the
  identifiers (the same reason family-cards-demo's CI uses generic
  PII shapes). Add one with
  `check_sanitize.py --hash-term "<term or email>"`. Any email-shaped
  string outside Andrew's allowlisted public identity also hits.
  Identifier hits cannot be excepted by a repo-local file.
- **Topics** (the sensitive categories, as terms plus a
  dollar-amount pattern) also hit, and every hit is quoted in the
  output so false positives stay visible and tunable. A scanned repo
  may carry `sanitize-exceptions.json` with path+term-scoped,
  reasoned exceptions for the topic class only — the known cases are
  a redaction filter's own word list and invented-data fixtures that
  exist to prove the filter works. Excepted hits still print.
- Andrew's own public identity (name, handles/domains, public email
  addresses) is allowlisted in the term file and masked before
  scanning — he is public on purpose.

Wiring: the portfolio and family-cards-demo each carry a
`sanitize-gate.yml` workflow that checks out fleet-kit and runs the
checker over their own tree on push/PR — the same check family as
the publish gate (which checks link permission; this checks
content).

**The fallback is visible, not silent** (Andrew, Oct 29, 2026).
`scripts/pull_sanitize.py` runs the same checker across every
public-posture project's tree and records the results in the
generated overlay above. The private section's generator reads the
overlay at build time: a repo recorded as failing keeps its cards
in the **owner** dataset carrying a generated tag —
**"Sanitizer needed"** — with the causing matches quoted in the
build report, and is dropped from the **family** dataset entirely.
The tag is generated from the gate result, never hand-set in a
manifest; a stale overlay (its recorded manifest SHA no longer
matches the pulled manifest) is ignored with a warning rather than
applied. Owner-only, never family, and the owner can see exactly
which repo is held back and why.

## Sanitization pass — the fix path behind the tag

The gate detects; the pass remediates.
[`scripts/sanitize_packet.py`](../scripts/sanitize_packet.py)
(stdlib only) turns a failing repo's gate result into a work
packet, applies the packet's dispositions on a branch, and
re-gates the branch before anything is proposed for merge:

- **build** — scan a repo fresh (pulled tree, or a local checkout)
  and emit `packets/<repo>.json`: one entry per unexcepted hit,
  each with an empty `disposition` slot. Identifier hits are
  recorded as SHA-256 digests + file/line only — never the value,
  never quoted context, because this repo is public and a packet
  must not publish what it exists to remove. Topic hits carry the
  term, a quoted window, and an `anchor` (the exact matched text).
- **dispositions** — `generalize` (apply the packet's `draft` as
  an anchored exact-match replacement; an anchor that does not
  match exactly once fails the whole apply), `substitute` (swap
  an identifier for the invented replacement in the target repo's
  `sanitize-substitutions.json`, keyed by the identifier's hash —
  the pass applies table entries, it never invents replacements
  for real data; the Emma/Noah build of the demo is the
  precedent), `relocate` (git-mv the file into the packet's
  relocate dir, default `private-staging/`, with a generic stub
  at the original path only where the packet specifies one), and
  `except` (a reasoned entry in the repo's
  `sanitize-exceptions.json` — topic class only, reason
  mandatory, the checker's own validation).
- **apply** — validates everything first (nothing is touched on a
  refusal), edits on a `sanitize-pass/<date>` branch, commits,
  and re-gates: the packet closes only when the branch scan is
  clean-or-excepted. Re-running apply is idempotent — already-done
  hits report as already-applied. `--push`/`--pr` push the branch
  and open a PR with the packet summary as its body. Merging
  stays Andrew's word, and merging does NOT itself clear the
  "Sanitizer needed" tag — the tag is build-generated from the
  overlay and clears when the overlay is regenerated after merge
  and shows the repo passing.
- **relocation staging** — the checker skips directories named
  `private-staging` (a named carve-out in
  `scripts/check_sanitize.py`), so a relocated file leaves the
  scanned surface. Staged content in a public repo is still in a
  public repo — off-surface, NOT secret — and the follow-up move
  behind the gate, or deletion, stays an owner decision.

The end-to-end check is
[`scripts/test_sanitize_pass.py`](../scripts/test_sanitize_pass.py):
it seeds a synthetic fixture (one identifier hit, one
generalizable hit, one relocatable file, one except-able hit) and
proves packet → dispositions → branch apply → re-gate clean,
plus the refusal paths. Its fixture strings are the reasoned
exception recorded in fleet-kit's own sanitize-exceptions.json.
